# 03 · 2D 与 3D：选型与关键区别

> 配套 demo：[`godot-demo/03-2d-vs-3d/`](https://github.com/shenjunjian/wasm-road-blog/tree/main/godot-demo/03-2d-vs-3d/)
>
> 截图清单见文末。

第 02 章你知道了"场景 = 一棵节点树"——但树根用什么节点、节点怎么渲染，这取决于**这个项目是 2D 还是 3D**。这一章把"为什么 Godot 要把 2D 和 3D 拆成两套几乎独立的节点体系"这件事讲透，包括坐标系、摄像机、Z 排序、深度缓冲、美术资产、性能取舍。读完你会有两个能力：

1. 在动手前判断「这个项目用 2D 还是 3D」
2. 混用 2D / 3D 时知道怎么把它们"缝合"在同一棵场景树里

---

## 1. 一张总览表先放这

| 维度 | 2D | 3D |
| --- | --- | --- |
| 根节点类型 | `Node2D` / `Control` | `Node3D` |
| 渲染对象基类 | `CanvasItem` | `Node3D` |
| 坐标系 | 像素 (x, y) + z_index | 世界单位 (x, y, z) |
| 摄像机 | `Camera2D` | `Camera3D` |
| 投影 | 平行投影（默认） | 透视 / 平行 |
| 前后关系 | **Z-index + y-sort**（程序员显式声明） | **深度缓冲**（GPU 自动算） |
| 物理服务器 | `PhysicsServer2D` | `PhysicsServer3D` |
| 物理节点 | `StaticBody2D` / `RigidBody2D` / `CharacterBody2D` / `Area2D` | `StaticBody3D` / `RigidBody3D` / `CharacterBody3D` / `Area3D` |
| 美术资产 | 像素图 / sprite sheet / 矢量 | 模型（glTF / FBX）+ 贴图 + 材质 |
| 默认单位 | 1 像素 = 1 单位（除非用 Camera2D zoom 改） | 1 米 = 1 单位 |
| 默认渲染管线 | Forward+（与 3D 共享） | Forward+ / Mobile / Compatibility |
| 中低端设备适配 | 几乎不用适配 | 经常要降级管线 / LOD |

这一章会逐项拆。

## 2. 节点类型：CanvasItem 体系 vs Node3D 体系

第 02 章说过，节点类型决定它能干什么。2D 和 3D 的差异从**根节点类型**就开始分叉：

```text
Object
└── Node
    ├── CanvasItem                       ← 2D 渲染基类
    │   ├── Node2D                       ← 2D 空间变换
    │   │   ├── Sprite2D
    │   │   ├── AnimatedSprite2D
    │   │   ├── Polygon2D
    │   │   ├── Line2D
    │   │   ├── MeshInstance2D            ← 罕见：把 3D 网格放 2D 场景
    │   │   ├── Camera2D
    │   │   ├── CollisionObject2D
    │   │   │   ├── Area2D
    │   │   │   └── PhysicsBody2D
    │   │   │       ├── StaticBody2D
    │   │   │       ├── RigidBody2D
    │   │   │       └── CharacterBody2D
    │   │   └── …（约 30 个 2D 子类）
    │   └── Control                       ← 2D UI 基类
    │       ├── Container
    │       ├── Button / Label / LineEdit / …
    │
    └── Node3D                            ← 3D 渲染基类
        ├── MeshInstance3D                ← 3D 模型
        ├── Camera3D
        ├── Light3D                       ← DirectionalLight3D / OmniLight3D / SpotLight3D
        ├── CollisionObject3D
        │   ├── Area3D
        │   └── PhysicsBody3D
        │       ├── StaticBody3D
        │       ├── RigidBody3D
        │       └── CharacterBody3D
        └── …（约 25 个 3D 子类）
```

### 2.1 关键事实

- **`Node2D` 与 `Node3D` 互不继承**——它们都是从 `Node` 派生的兄弟类。一个 2D 节点的 `position` 是 `Vector2`，3D 是 `Vector3`。
- **同一棵场景树里可以混用**——根是 `Node3D`，下面挂个 `CanvasLayer` + 2D UI 节点；或者根是 `Node2D`，下面挂个 `Sprite3D` 显示 3D 模型。最常见的混搭是 3D 游戏 + 2D HUD。
- **物理节点也分 2D / 3D**——`Area2D` 不会和 `Area3D` 互相作用，因为它们跑在不同的物理世界里。

> 关键认知：**2D 和 3D 在 Godot 里是两套独立的「渲染 + 物理」管道**。它们通过场景树结构（CanvasLayer、子节点）实现协作，但内部不共享任何状态。

### 2.2 在编辑器里切换工作空间

Viewport 顶部的 **2D / 3D 按钮**只是切换**编辑器视角**——根节点是 `Node2D` 时即使你点 3D 也看不到 3D 坐标系，反之亦然。

> 截图占位：`<img src="/godot/03-01-editor-2d-3d.png" />`（同一项目里分别打开 2D 和 3D 场景时 Viewport 顶部按钮的状态对比）

## 3. 坐标系差异：像素 vs 世界单位

### 3.1 2D 坐标：像素 = 1 单位

`Node2D.position` 是 `Vector2(x, y)`，默认单位是**屏幕像素**。窗口大小 1280×720，那 position.x 在 0 ~ 1280 之间就是"屏幕里可见"的范围。

```gdscript
extends Node2D

@export var speed: float = 200.0

func _process(delta: float) -> void:
    position += Vector2(speed * delta, 0)
```

注意 2D 节点还有一个 **`z_index` 属性**（`int`，可以是负数）——它**不影响坐标**，只影响渲染时的绘制顺序。`z_index` 越大的画得越靠前（盖在上层），同 `z_index` 按场景树顺序画。这就是为什么 2D 没有"深度缓冲"也要支持前后遮挡。

`y_sort_enabled`：开了之后，**y 坐标小的画得靠后**（即远处在上）。这是 2D 平台游戏做"角色走到树后面被树挡住"的常用手法。

> 截图占位：`<img src="/godot/03-02-2d-zindex.png" />`（同一画面中 z_index 不同造成的前后遮挡效果）

### 3.2 3D 坐标：1 米 = 1 单位

`Node3D.position` 是 `Vector3(x, y, z)`，单位是**米**。这是 Godot 与 Unity / Unreal 一致的约定——把"1 单位"想象成"1 米"。

```gdscript
extends Node3D

@export var speed: float = 5.0  # 米/秒

func _process(delta: float) -> void:
    position += Vector3(speed * delta, 0, 0)
```

3D 节点**没有 z_index**——前后遮挡由 GPU 的**深度缓冲（depth buffer / z-buffer）**自动算：

```text
View
─────────────────────────►
│
│  ← 摄像机视线方向
│
▼
```

每个像素在绘制时，GPU 会把"它到摄像机的距离"写到一张额外的纹理（depth buffer）里。下一个像素想画时，如果它比现有像素更远，GPU 就**直接丢弃**——自动形成"前面挡住后面"的效果，**不需要程序员声明任何 z_index**。

### 3.3 两个体系不能混用 position

```gdscript
extends Node2D

func _ready() -> void:
    position = Vector3(1, 2, 3)   # ❌ 编译报错：Node2D.position 是 Vector2
    position = Vector2(640, 360)   # ✅
```

Godot 用强类型杜绝这种错误。GDScript 的静态类型（第 05 章细讲）会在写代码时就报红，不用等到运行时。

## 4. 摄像机：Camera2D vs Camera3D

摄像机决定"玩家看到的世界"。2D 和 3D 的摄像机工作原理差别很大。

### 4.1 Camera2D：决定画布的"取景框"

> 截图占位：`<img src="/godot/03-03-camera-2d.png" />`（Camera2D 节点在场景树里的位置 + Inspector 的 Zoom 字段）

```gdscript
extends Camera2D

@export var follow: Node2D   # 跟随的目标（如 Player）

func _ready() -> void:
    make_current()            # 把自己设为当前摄像机（必须！）

func _process(delta: float) -> void:
    if follow:
        # 平滑跟随：position 用 lerp 让相机慢慢追上
        position = position.lerp(follow.position, 5.0 * delta)
```

**Camera2D 的关键属性**：

| 属性 | 含义 |
| --- | --- |
| `zoom` | 放大倍数。`Vector2(2, 2)` = 放大 2 倍；`Vector2(0.5, 0.5)` = 缩小一半（看到更多东西） |
| `offset` | 视口偏移。一般用于"玩家偏左 / 偏右"的相机 |
| `limit_left/right/top/bottom` | 摄像机不会越过这些边界（防止看到场景外） |
| `position_smoothing_enabled` | 是否平滑移动。开了之后 `position` 会自动 lerp |

**Camera2D 没有"投影"概念**——它永远是平行投影（没有透视效果），因为 2D 场景里所有像素都直接映射到屏幕。

### 4.2 Camera3D：决定 3D 世界的"取景椎体"

> 截图占位：`<img src="/godot/03-04-camera-3d.png" />`（Camera3D 节点的属性面板 + 在场景里显示的椎体预览线框）

Camera3D 的核心属性：

| 属性 | 含义 |
| --- | --- |
| `fov` (degrees) | 视野角度（透视投影的"鱼眼"程度）。默认 75°，FPS 一般用 60~90° |
| `near` / `far` | 近 / 远裁剪面。比 near 靠近或比 far 远的东西不会被渲染 |
| `projection` | 透视（`PROJECTION_PERSPECTIVE`）或平行（`PROJECTION_ORTHOGONAL`） |
| `current` | 是否是当前激活的相机。同一帧可以有多个 Camera3D，但只有一个是 `current` |

```gdscript
extends Camera3D

@export var target: Node3D     # 跟随目标
@export var distance: float = 10.0  # 相机离目标的距离
@export var height: float = 5.0     # 相机比目标高多少

func _process(delta: float) -> void:
    if target:
        # 相机固定在 target 后上方
        global_position = target.global_position + Vector3(0, height, distance)
        look_at(target.global_position, Vector3.UP)
```

**透视 vs 平行投影**：

- **透视**：远处的物体会变小——模拟人眼，做 FPS / TPS / 3D 平台跳跃用这个。
- **平行**：远处物体不缩小——模拟工程图，做 RTS / 战术俯视角游戏用这个（如《全面战争》《城市天际线》）。

### 4.3 多个摄像机切换

```gdscript
# 切到过场相机
$CutsceneCamera.make_current()
# 切回玩家相机
$PlayerCamera.make_current()
```

`make_current()` 是立即切换；`Camera3D` 还有 `set_current_with_transition(tween)` 做平滑过渡。

> **Camera2D 在 Node2D 子树里才生效，Camera3D 在 Node3D 子树里才生效**。把它们放错位置不会报错，但也不会起作用。

## 5. Z 排序 vs 深度缓冲：原理差异

这是 2D / 3D **最本质的渲染差异**，必须搞懂。

### 5.1 2D：靠程序员（或引擎辅助）显式声明顺序

2D 渲染流程（简化）：

```text
每一帧：
1. 收集所有 CanvasItem 子树
2. 按 z_index 升序排序
3. 同 z_index：开了 y-sort 的按 y 排序
4. 同 y-sort / 都没开：按场景树顺序
5. 依次把每个 CanvasItem 提交给 GPU（2D 批处理）
6. 完事了——不存在"深度测试"，画上去就盖住前面
```

**为什么 2D 没有深度缓冲？** 因为 2D 像素只占 1 个 framebuffer attachment，省一张 depth texture 能省一半显存带宽。这也是为什么 2D 引擎在低端机上跑得飞快。

代价：**遮挡关系得程序员手动告诉引擎**。

```gdscript
# 平台跳跃游戏：玩家走到树后要被挡住
@onready var tree_sprite: Sprite2D = $Tree
@onready var player: Sprite2D = $Player

func _process(_delta: float) -> void:
    if player.global_position.y < tree_sprite.global_position.y:
        tree_sprite.z_index = 0     # 树在前（盖住玩家）
        player.z_index = -1
    else:
        tree_sprite.z_index = -1    # 玩家在前（盖住树）
        player.z_index = 0
```

更优雅的做法：开 **`y_sort_enabled = true`**，引擎自动按 y 排序——但只对**相同 z_index** 的节点有效。

### 5.2 3D：GPU 自动算深度

3D 渲染流程（简化）：

```text
每一帧：
1. Vertex Shader：每个顶点算出"在摄像机坐标系里的位置"（含深度 z 值）
2. Rasterization：把三角形光栅化成像素，每个像素携带"插值出来的深度"
3. Fragment Shader：算颜色 + 比较当前像素的深度与 depth buffer
4. 如果当前像素比 depth buffer 里记录的更远 → 丢弃（early-z）
5. 否则写入颜色 + 更新 depth buffer
```

这套机制 GPU 硬件加速，自动搞定**所有**前后遮挡关系。代价：每帧多一次深度纹理读写。

**3D 不用 z_index**——但有 `render_priority`（少见，用于强制覆盖默认渲染顺序，比如透明物体强制最后画）。

### 5.3 透明物体的差异

透明物体在 2D 和 3D 里有同样的麻烦：**后画的覆盖先画的**。但处理方式不同：

| 维度 | 2D | 3D |
| --- | --- | --- |
| 透明混合 | 默认 blend_mix | alpha blend |
| 排序依据 | z_index + y-sort | 摄像机距离（far-to-near） |
| 容易出问题 | 自重叠（同一 z_index 内画自己两次） | 自相交（同一个 mesh 内 alpha 排序错乱） |
| 解决方案 | 用 `light_mask` / 拆分 sprite | alpha-test（cutout）或 Pre-multiplied Alpha |

WebGPU 系列第 06 章专门讲过透明排序，逻辑跟这里通用。

## 6. 美术资产：像素图 vs 模型

2D 和 3D 的资产工作流完全不同。

### 6.1 2D 资产

| 资产类型 | 文件 | Godot 导入后类型 |
| --- | --- | --- |
| 像素图 / 矢量图 | PNG / JPG / SVG / WebP | `CompressedTexture2D` |
| Sprite 动画序列帧 | 多张 PNG 或单张 sprite sheet | `SpriteFrames`（AnimatedSprite2D 用） |
| 瓦片图集 | 多张瓦片 PNG | `TileSetAtlas`（TileMap 用） |
| 字体 | TTF / OTF / WOFF / WOFF2 | `FontFile` |
| 音频 | WAV / OGG / MP3 | `AudioStream` |

**Sprite sheet**（精灵图集）是把一张大图切成多个小精灵——2D 游戏的标配，原因是 GPU 喜欢"一次画很多"而不是"反复切贴图"。

```gdscript
# 加载 sprite sheet 的某一块
var region := Rect2(0, 0, 64, 64)
$Sprite.texture.region_enabled = true
$Sprite.texture.region_rect = region
```

### 6.2 3D 资产

| 资产类型 | 文件 | Godot 导入后类型 |
| --- | --- | --- |
| 模型 | glTF / GLB（推荐）/ FBX / OBJ / DAE | `Mesh` + `PackedScene` |
| 贴图 | PNG / JPG / EXR / HDR | `CompressedTexture2D` / `Texture2D` |
| PBR 材质 | 在模型里嵌入 / `.tres` 文件 | `StandardMaterial3D` |
| 环境贴图 | HDR / EXR | `Environment` / `PanoramaSky` |
| 骨骼动画 | 模型内嵌 / `.glb` | `AnimationLibrary` |

**glTF / GLB 是 Godot 4.x 推荐的 3D 资产格式**——开源、二进制、包含网格 / 材质 / 动画 / 蒙皮一个不漏。FBX 是 Unity / Unreal 时代的遗留物，能用但容易出兼容问题。

> **Godot 没有官方 DCC（建模工具）**——Blender 是默认搭档。本系列不展开讲 Blender，但所有 demo 都假设你已经有 .glb 文件。

### 6.3 关键差异：UV 与材质

| 概念 | 2D | 3D |
| --- | --- | --- |
| UV | 大多不需要（整张图直接贴） | 模型表面所有顶点都有 UV，UV 把"贴图像素"映射到"模型表面" |
| 材质 | Sprite2D 只有一个 texture | PBR 材质 4 大属性：Albedo / Metallic / Roughness / Emission |
| 多通道 | Sprite 用 atlas 切片 | 模型有 base color / normal / metallic-roughness / occlusion 多张贴图 |

第 09 章会专门讲 3D PBR 材质。

## 7. 性能取舍：什么时候用 2D / 3D

| 场景 | 推荐 | 理由 |
| --- | --- | --- |
| 平台跳跃（空洞骑士、蔚蓝） | 2D | 像素精度高、关卡设计直观 |
| Roguelike 卡片（Hades、Slay the Spire） | 2D | UI 重，3D 是浪费 |
| 沙盒生存（星露谷、泰拉瑞亚） | 2D | 大世界，2D TileMap 更省 |
| 战术 RPG（火焰纹章） | 2D | 网格天然适合 2D |
| MOBA（英雄联盟、DOTA2） | 3D | 角色需要旋转，3D 表现力强 |
| FPS / TPS（CS、使命召唤） | 3D | 必须 3D |
| 开放世界 ARPG（塞尔达、原神） | 3D | 探索 + 视角 |
| 解谜（纪念碑谷） | 2D + 3D 视角 | 2.5D |
| 模拟经营（文明、城市天际线） | 3D | 需要旋转视角 |
| 剧情冒险（极乐迪斯科） | 2.5D / 3D | 看预算 |

**性能数字**（粗略）：

| 项目类型 | 2D 帧时间（低端机） | 3D 帧时间（低端机） |
| --- | --- | --- |
| 简单场景（100 个 sprite / mesh） | < 4 ms | ~8 ms |
| 复杂场景（粒子 + 阴影） | ~8 ms | ~16 ms |
| 满特效（屏幕后处理） | ~12 ms | ~25 ms+ |

**结论**：如果项目在 2D 表现力够用，就别上 3D。3D 的开发成本（建模、骨骼动画、灯光、阴影、shader 调试）是 2D 的 3~5 倍。

## 8. 混用 2D / 3D：3 种模式

### 8.1 模式 A：3D 世界 + 2D HUD（最常见）

```text
World (Node3D)               ← 根节点是 Node3D
├── Terrain (MeshInstance3D)
├── Player (CharacterBody3D)
└── UI (CanvasLayer)         ← CanvasLayer 是 CanvasItem 子树，可以挂 2D UI
    ├── HUD (Control)
    └── PauseMenu (Control)
```

`CanvasLayer` 是连接 Node3D 子树与 2D 渲染的关键节点——它**渲染在自己的画布上**，不会受 3D 摄像机影响（无论你怎么转 3D 相机，HUD 永远在屏幕同一位置）。

### 8.2 模式 B：2D 世界 + 3D 装饰（少见的复古风）

```text
World (Node2D)               ← 根节点是 Node2D
├── Background (Sprite2D)
├── Player (CharacterBody2D)
└── Coin (Sprite3D)          ← 3D 旋转的金币，在 2D 场景里
```

`Sprite3D` 是 3D 节点但只有 1 个面（朝向摄像机），相当于"会 3D 旋转的 Sprite"。

### 8.3 模式 C：2.5D（多视角）

```text
Root (Node3D)
├── Map (Node3D)             ← 整个地图用 3D 网格
└── Camera3D
    ├── projection = PROJECTION_ORTHOGONAL
    └── rotation = Vector3(-PI/4, -PI/4, 0)
```

`Camera3D` 用**平行投影** + **斜 45° 旋转**，就是《暗黑破坏神》《模拟城市》的"伪 3D"。美术用 3D 模型但渲染出来是 2D 视角。

## 9. demo：同屏对比 2D 与 3D

demo 放在 `godot-demo/03-2d-vs-3d/`，故意做成一个**主场景里同时显示 2D 和 3D 子场景**的小示例。

> 截图占位：`<img src="/godot/03-05-mixed-demo.png" />`（demo 运行截图——上半屏 2D 方块在左右移动，下半屏 3D 立方体在旋转 + 透视）

### 9.1 文件清单

```
03-2d-vs-3d/
├── README.md
├── project.godot
├── Main.tscn               ← 根 Node3D，混搭上下半屏
├── World2D.tscn            ← 2D 子场景：精灵左右移动
├── World3D.tscn            ← 3D 子场景：立方体旋转
└── scripts/
    ├── Main.gd
    ├── World2D.gd
    └── World3D.gd
```

### 9.2 `Main.tscn` 关键结构

```ini
[gd_scene load_steps=5 format=3]

[ext_resource type="Script" path="res://scripts/Main.gd" id="1_main"]
[ext_resource type="PackedScene" path="res://World2D.tscn" id="2_2d"]
[ext_resource type="PackedScene" path="res://World3D.tscn" id="3_3d"]

[sub_resource type="BoxMesh" id="BoxMesh_1"]

[node name="Main" type="Node3D"]
script = ExtResource("1_main")

; 上半屏：2D 子场景，通过 CanvasLayer 隔离
[node name="CanvasLayer" type="CanvasLayer" parent="."]
layer = 1

[node name="World2D" parent="CanvasLayer" instance=ExtResource("2_2d")]
offset_top = 0.0
offset_bottom = 360.0

; 下半屏：3D 子场景
[node name="World3D" parent="." instance=ExtResource("3_3d")]
transform = Transform3D(1, 0, 0, 0, 1, 0, 0, 0, 1, 0, -1, -3)
```

### 9.3 `scripts/World2D.gd`

```gdscript
extends Node2D

@export var speed: float = 200.0
var _direction: int = 1

func _process(delta: float) -> void:
    position.x += speed * delta * _direction
    # 限制在父 CanvasLayer 给的 1280x360 范围内
    if position.x > 640:
        position.x = 640
        _direction = -1
    elif position.x < -640:
        position.x = -640
        _direction = 1
```

### 9.4 `scripts/World3D.gd`

```gdscript
extends Node3D

@export var rot_speed: float = 1.0  # 弧度/秒

func _process(delta: float) -> void:
    rotate_y(rot_speed * delta)
```

> 这个 demo 不做完整可交互（避免章节越长越复杂），目的是让你直观看到 2D / 3D 子场景在同一棵场景树里跑。

## 10. 易错清单

| 现象 | 原因 |
| --- | --- |
| 2D 项目里加 `Light3D` 不亮 | Light3D 是 3D 节点，必须挂 `Node3D` 子树，且 `CanvasItem` 不会受 3D 光照影响 |
| `Sprite2D` 用 `set_global_position` 不生效 | 应改 `global_position` 属性 |
| 3D 模型看起来很暗 | 没接灯光，或 `StandardMaterial3D` 没启用 `shading_mode` |
| 3D 模型全黑 | 法线方向反了；Godot 默认左手坐标系，模型从 Blender 导来要检查轴向 |
| Camera3D 在 Node2D 子树里没效果 | 摄像机要放在它要"看"的子树根节点附近 |
| `y_sort_enabled` 开了但遮挡还是错乱 | 父子节点 z_index 不同，y-sort 只对兄弟节点生效 |
| `z_index` 改了但 2D 画面没变 | 节点 `z_as_relative` 为 true 时是相对父节点的 z_index |

## 11. 章节小结

- **节点体系**：CanvasItem vs Node3D，两套独立的渲染与物理管道
- **坐标系**：2D 用像素 (x, y) + z_index；3D 用世界单位 (x, y, z)，靠深度缓冲
- **摄像机**：Camera2D 是 2D 取景；Camera3D 有透视 / 平行投影
- **前后排序**：2D 靠程序员显式声明 z_index；3D 靠 GPU 自动算
- **美术资产**：2D 是 PNG/sprite sheet；3D 是 glTF 模型 + 贴图 + PBR 材质
- **混用模式**：3D 世界 + 2D HUD（CanvasLayer）、2D 世界 + 3D 装饰（Sprite3D）、2.5D（平行投影）

下一章 [04 · 节点类型全览与重要节点详解](./04-node-types.md)，我们把 Godot 所有"会用到的"节点类型按继承层级分组遍历——读完你对每个节点能干什么心里有数，再写代码就知道该用什么节点。
